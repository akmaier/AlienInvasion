# Requirements: persistent highscore list and waves

**The change.** Changed ALIEN DESTRUCTION and SCORE INCREMENT; withdrew GAME END ALL ALIENS DESTROYED and SESSION HIGHSCORE RESET; added WAVE FIRST, WAVE NEXT, SESSION HIGHSCORE DISPLAY ENTRIES, SESSION HIGHSCORE KEPT ON NEW SESSION, SESSION HIGHSCORE KEPT ON RELOAD and SESSION HIGHSCORE COOKIE STORAGE; the rest of the section is as it stands.

**Why.** Issue #17 (akmaier/AlienInvasion, from mail `MAIL-e02513ea5c18cc58`) asks for a highscore list kept across game sessions in browser cookies and showing several players' initials and scores, and for waves: after the first 24 enemies wave 2 starts, each wave gives enemies one more hit point, and the wave state resets when a new game session starts. akmaier asked to change the requirements as the issue asks. The issue's sentences map to the SPEC as follows:
- "entries survive across game sessions" contradicts SESSION HIGHSCORE RESET ("reset to empty when a new game session starts"), which is therefore withdrawn. Surviving a new session and surviving a page reload are two things, so they are two requirements: SESSION HIGHSCORE KEPT ON NEW SESSION and SESSION HIGHSCORE KEPT ON RELOAD.
- "in browser cookies" is SESSION HIGHSCORE COOKIE STORAGE, a requirement of its own so that the storage medium can be checked apart from the persistence.
- "display multiple player names (initials) and their scores": SESSION HIGHSCORE DATA stores initials and SESSION HIGHSCORE DISPLAY GAMEOVER / DISPLAY INGAME require the list to be displayed, but no requirement names what a displayed entry shows. That is SESSION HIGHSCORE DISPLAY ENTRIES. That there are several names follows from keeping the list; SESSION HIGHSCORE LIMIT (at most ten) stays unchanged.
- "after the player destroys the first 24 enemies, start wave 2": the formation is 6 × 4 = 24 aliens (`FORMATION_COLS`, `FORMATION_ROWS`, src/game-logic/GameSession.js:24–25), so the first 24 enemies are all aliens of the first wave. WAVE NEXT states it for every wave and does not name the number, so that it still holds if the formation size changes. It contradicts GAME END ALL ALIENS DESTROYED ("the game shall end when every alien has been destroyed"), which is therefore withdrawn. The game then ends only by GAME OVER CONDITION.
- "each subsequent wave increases enemy hit‑points by +1 and requires one additional projectile hit": wave 1 needs one hit, wave n needs n hits. It contradicts ALIEN DESTRUCTION ("when a projectile collides with an alien, the alien shall be removed"), which is changed to remove an alien of wave n by exactly its n‑th hit.
- SCORE INCREMENT said "when a projectile collides with an alien". With more than one hit per alien that could mean a point for every hit. The issue does not say which, and the existing test checks the increment "on alien destruction"; the rule is changed to count a removed alien, which is what it does today.
- "Reset wave state when a new game session starts" is WAVE FIRST: every game session, the first after loading and every restart, begins with wave 1.

**Impact list.**
- SESSION HIGHSCORE RESET: withdrawn. This reverses entry 06, which kept it so that a restart by the button empties the list.
- GAME END ALL ALIENS DESTROYED: withdrawn. Its test `tests/integration/test_game_over.py::test_game_ends_when_all_aliens_destroyed` has to be removed.
- ALIEN DESTRUCTION, SCORE INCREMENT: changed; their tests keep their names and are extended to waves beyond 1.
- PLAYER SHIP SLOW SPECIAL SHOT ("can destroy up to three aliens in a single shot"): unchanged. From wave 2 on, the special projectile gives one hit to each of up to three aliens and destroys none in a single shot. The rule stays true because it is an upper bound. If the special shot is to destroy three aliens whatever their hit points, that is a further change the issue does not ask for.
- SESSION START STATE: unchanged. It names score, formation and ship; the wave is given by WAVE FIRST.
- KISS NO EXTRA FEATURES: unchanged. It names "multiple levels" as an example of an excluded feature; waves are now explicitly added by requirements, which its "unless a future requirement explicitly adds it" allows.
- IMPLEMENTATION JAVASCRIPT WEB requires the game to run by opening index.html without a server. Chromium-based browsers store no cookies for pages opened from a `file://` path by default. In those browsers, SESSION HIGHSCORE COOKIE STORAGE and SESSION HIGHSCORE KEPT ON RELOAD can then hold together only when the page is served over http(s). If the game is meant to be opened from disk, this entry should be rejected and SESSION HIGHSCORE COOKIE STORAGE dropped, leaving the storage to the architecture.
- The names SESSION HIGHSCORE … now describe a list that outlives a session. Renaming them would mean withdrawing and adding each one, and the issue keeps the name, so no rename is proposed.
- UC-003 (projectile flies and hits), UC-004 (game ends) and UC-006 (session highscores managed), and the architecture notes ARC-001, ARC-004, ARC-005 (which rejects persistence because of SESSION HIGHSCORE RESET), ARC-006 and MOD-game-logic, name the withdrawn or changed requirements. They will have to follow once this entry is accepted. So will HighscoreStore (src/game-logic/HighscoreStore.js) and GameSession (src/game-logic/GameSession.js).
